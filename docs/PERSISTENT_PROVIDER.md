# Persistent Worker Provider Design

The current `ipc_future_pool` engine is the portable correctness provider for
`arrow_ipc + multiprocess_parallel`. It now discovers UDF globals once at
registration/wrapper creation time, but it still constructs generic Future tasks
per DuckDB chunk. This document specifies the provider boundary for a later
persistent worker implementation without changing the no-hidden-fallback rule.

## Non-goals

- Do not change scalar UDF callback lifetime rules.
- Do not batch chunks whose DuckDB callback frames are not simultaneously active.
- Do not use R `serialize()`/`unserialize()` as a hidden transport for chunk
  input/output values on the hot data path. Control-plane serialization of
  functions/globals by an explicit provider such as `future` is allowed but must
  not be confused with chunk payload transport.
- Do not send raw `SEXP` pointers, external pointer addresses, or borrowed
  DuckDB vector storage to worker processes.
- Do not silently fall back to same-process execution when a multiprocess
  provider fails.

## Provider contract

A provider should be an R-side object/list with these operations:

```r
provider$start(plan)
provider$stop()
provider$register_udf(
  udf_id,
  udf_name,
  fun,
  arg_types,
  return_type,
  mode,
  null_handling,
  exception_handling,
  output_schema_spec,
  globals,
  packages
)
provider$submit(udf_id, chunk_id, row_count, input_ipc_payload, timeout_ms = NULL)  # -> task_id
provider$collect_any(max_results = Inf, timeout = NULL)          # -> results
provider$collect_many(task_ids, timeout = NULL)                  # -> results
provider$cancel(task_ids)
provider$stats()
```

`future` can implement this as an adapter even if each `submit()` still creates a
Future. Persistent providers should load `fun`, globals, packages, type
descriptors, and schema specs once in `register_udf()`, then send only task
metadata and Arrow IPC bytes per chunk.

## Registration envelope

Registration is database-runtime/UDF scoped, not connection scoped:

```text
register_udf
  provider_runtime_id
  udf_id
  udf_name
  engine_id = ipc_future_pool | ipc_mirai_pool | ipc_nanonext_pool | ...
  mode = scalar | vectorized
  arg_types
  return_type
  null_handling
  exception_handling
  output_schema_spec
  globals
  packages
```

The provider must acknowledge registration before SQL UDF registration succeeds
for engines that require preloaded workers. For the generic Future adapter, this
acknowledgement can be local because workers receive the precomputed globals in
each task.

## Task envelope

The caller submits only `udf_id`, `chunk_id`, `row_count`, optional
`timeout_ms`, and owned Arrow IPC bytes. After accepting the task, the provider's
internal task envelope contains only owned, process-safe data:

```text
task
  task_id
  udf_id
  udf_name           # diagnostic; udf_id remains the authoritative key
  chunk_id
  row_count
  timeout_ms         # provider/task timeout budget supplied to submit(), if any
  cancel_token       # provider-generated cancellation capability, if supported
  input_ipc_payload  # R raw vector containing Arrow IPC bytes
```

The input payload is owned bytes. It is not an external pointer and not a view
into a DuckDB callback frame. `udf_name` is registered once in `register_udf()`
and copied into tasks only for diagnostics. `cancel_token` is generated by the
provider when a task is accepted and is returned/observable through provider
state for `cancel(task_ids)`; callers do not invent cancellation capabilities.

## Result envelope

```text
result
  task_id
  udf_id
  chunk_id
  status = ok | error | cancelled | timeout
  cancel_token       # echoed when provider supports cancellation
  output_ipc_payload  # present only for ok
  error_message       # present for error/cancelled/timeout
  worker_pid          # optional diagnostic
  timing              # optional encode/submit/eval/decode/writeback timings
```

The collector must preserve task/chunk identity so the main process can write
results back to the correct blocked DuckDB callback output vector. Result payloads
are Arrow IPC bytes and are copied/imported into DuckDB-owned output vectors.

## Backpressure and cancellation

Scalar UDF callbacks borrow DuckDB callback-frame storage until the callback
returns. Therefore, the first persistent implementation should support:

- bounded submit queue size;
- collect-any to release blocked callbacks as soon as results arrive;
- pending cancellation before a worker starts a task;
- deterministic query errors for worker failure or provider shutdown.

Running same-process requests cannot be cancelled safely without an owned input
snapshot and owned result/writeback design. That is a separate architecture item.

## Transport decision

The transport order is:

1. Keep `future_provider` as the portable correctness/reference adapter.
2. Implement `mirai_provider` first for persistent workers, because mirai daemon
   processes can preload evaluator/schema state and fit the provider contract
   without linking against private native symbols.
3. Consider `nanonext_provider` only after the mirai path proves that lower-level
   collect-any, backpressure, or notification control is necessary.

Do not link against uninstalled `nanonext.so` internals or any private package
symbols. If nanonext is used later, use its public R/native API surface and keep
all transport code behind the provider boundary.

## Candidate providers

- `future_provider`: portable reference adapter; correctness first; per-task
  Future overhead remains.
- `mirai_provider`: preferred first persistent-process provider because daemon
  workers can preload evaluator/schema state and avoid spawning work from
  scratch per chunk.
- `nanonext_provider`: lower-level request/reply or pipeline transport when the
  provider needs explicit collect-any, backpressure, and notification primitives.

Provider selection must be explicit in the engine ID. A failed persistent
provider must raise a clear Rducks/DuckDB error rather than silently executing via
another provider.
